The query interface contains three optional fields.

- `filter`
- `paging`
- `sorting`

All examples will be based on the following class.

```ts
interface MyClass {

  title: string
  completed: boolean
  age: number
}
```

## Filtering[​](#filtering 'Direct link to Filtering')

The `filter` field allows the filtering of fields based on the shape of the object the filter is used for.

See the [filter reference](#filter-reference) for a complete list of comparisons available.

<Note>
  The `Filter` interface is typesafe and the typescript compiler will complain if you include extra fields that are not present on
  the type you are creating the query for.
</Note>

Lets create a simple filter that would allow us to filter for titles equal to `'Foo Bar'`

### Simple[​](#simple 'Direct link to Simple')

```ts
import { Query } from '@ptc-org/nestjs-query-core'

const q: Query<MyClass> = {
  filter: {
    title: { eq: 'Foo Bar' }
  }
}
```

### Multiple Fields[​](#multiple-fields 'Direct link to Multiple Fields')

You can also filter on multiple fields.

```ts
import { Query } from '@ptc-org/nestjs-query-core'

const q: Query<MyClass> = {
  filter: {
    // title = 'Foo Bar' AND completed IS TRUE and age > 10
    title: { eq: 'Foo Bar' },
    completed: { is: true },
    age: { gt: 10 }
  }
}
```

### Multiple Comparisons on a single field.[​](#multiple-comparisons-on-a-single-field 'Direct link to Multiple Comparisons on a single field.')

If you include multiple comparisons for a single field they will be ORed together.

```ts
import { Query } from '@ptc-org/nestjs-query-core'

const q: Query<MyClass> = {
  filter: {
    // title = 'Foo Bar' OR field LIKE '%foo%'
    title: { eq: 'Foo Bar', like: '%foo%' }
  }
}
```

### And/Or[​](#andor 'Direct link to And/Or')

The filter also allows for more complex `and` and `or` filters. The `and` and `or` accept an array of filters allowing for nested complex queries.

In this example we `AND` two filters for the same property together: `age >= 10 AND age <= 20`.

```ts
const q: Query<MyClass> = {
  filter: {
    and: [{ age: { gte: 10 } }, { age: { lte: 20 } }]
  }
}
```

In this example a simple `OR` condition is created: `age >= 10 OR title NOT LIKE '%bar'`

```ts
const q: Query<MyClass> = {
  filter: {
    or: [{ age: { gte: 10 } }, { title: { notLike: '%bar' } }]
  }
}
```

This example combines `AND` and `OR` filters: `age >= 10 AND (title LIKE '%bar' OR title = 'foobar')`.

```ts
const q: Query<MyClass> = {
  filter: {
    and: [
      { age: { gte: 10 } },
      {
        or: [{ title: { like: '%bar' } }, { title: { eq: 'foobar' } }]
      }
    ]
  }
}
```

## Relation Join Conditions[​](#relation-join-conditions 'Direct link to Relation Join Conditions')

A filter on a relation adds its conditions to the `WHERE` clause, so it selects the records that
*have* a matching related record.

```ts
// every todo item that has a sub task whose title starts with 'Discuss'
const q: Query<TodoItem> = {
  filter: { subTasks: { title: { like: 'Discuss%' } } }
}
```

That is the right question to ask most of the time, but it cannot express "every todo item, joined
only to the sub tasks that match". The relation is joined with a `LEFT JOIN`, and a `WHERE` clause
over the joined rows drops the todo items that have no matching sub task along with them.

The reserved `joinOn` key carries its conditions into the relation's `JOIN ... ON` clause instead,
where they decide which related rows are joined without deciding which records are returned.
`relationJoinCondition` builds the filter, and keeps the conditions typed against the relation:

```ts
import { Query, relationJoinCondition } from '@ptc-org/nestjs-query-core'

// LEFT JOIN "sub_task" ON "sub_task"."todo_item_id" = "todo_item"."id" AND "sub_task"."title" LIKE 'Discuss%'
const q: Query<TodoItem> = {
  filter: { subTasks: relationJoinCondition<SubTask>({ title: { like: 'Discuss%' } }) }
}
```

`joinOn` composes with the rest of the relation's filter: what sits beside it is still a `WHERE`
clause over the joined rows. This asks for every todo item that has *no* sub task matching the
conditions, an anti join:

```ts
const q: Query<TodoItem> = {
  filter: {
    subTasks: {
      ...relationJoinCondition<SubTask>({ title: { like: 'Discuss%' } }),
      id: { is: null }
    }
  }
}
```

### Where the key is valid[​](#where-the-key-is-valid 'Direct link to Where the key is valid')

`joinOn` is valid in exactly one place: the filter of a relation, reached from the filter of the
entity that relation belongs to. Anywhere else there is no single `JOIN` its conditions could belong
to, so the key raises an `InvalidRelationJoinConditionError` rather than being dropped from the
query.

- Not at the root of a filter. A filter of the records a query returns has no `JOIN` of its own.
- Not inside an `and` or an `or`. A relation referenced from several branches is joined once for all
  of them.
- Not nested inside another `joinOn`. An `ON` clause constrains the one relation being joined.
- The conditions under `joinOn` can only compare fields of the relation being joined. A condition on
  a relation of that relation would need a `JOIN` of its own, which an `ON` clause has nowhere to
  put.

A relation is joined once however many filters reference it, so a query whose own filter and whose
selected relation filter both carry conditions for the same relation is refused for the same reason.

<Note>
  `joinOn` is a reserved word in the filter language, not a property of any one entity. A relation
  whose entity has a filterable property called `joinOn` cannot be filtered on that property through
  a relation filter.
</Note>

<Note>
  `joinOn` is honoured by `@ptc-org/nestjs-query-typeorm`. The query services of the other
  persistence packages reject a filter carrying it with an `UnsupportedRelationJoinConditionError`,
  rather than reading `joinOn` as the name of a field and answering a different question. The key is
  not exposed in the generated GraphQL schema, so it is written in server code - an authorizer
  filter, a `queryService.query(...)` call, or a custom resolver.
</Note>

## Paging[​](#paging 'Direct link to Paging')

The `core` package defines a basic paging interface has two optional fields `limit` and `offset`.

<Tabs>
  <Tab title="Limit And Offset">
    ```ts
    const q: Query<MyClass> = {
      paging: {
        limit: 10,
        offset: 10,
      },
    };
    ```
  </Tab>

  <Tab title="Limit">
    ```ts
    const q: Query<MyClass> = {
      paging: {
        limit: 20,
      },
    };
    ```
  </Tab>

  <Tab title="Offset">
    ```ts
    const q: Query<MyClass> = {
      paging: {
        offset: 10,
      },
    };
    ```
  </Tab>
</Tabs>

## Sorting[​](#sorting 'Direct link to Sorting')

The `sorting` field allows to specify the sort order for your query.

The `sorting` field is an array of object containing:

- `field` - the field to sort on
- `direction` - `ASC` or `DESC`
- `nulls?` - Optional nulls sort, `NULLS_FIRST` or `NULLS_LAST`

<Tabs>
  <Tab title="Single-Sort">
    ```ts
    // import { SortDirection } from '@ptc-org/nestjs-query-core';
    const q: Query<MyClass> = {
      sorting: [{ field: 'title', direction: SortDirection.DESC }],
    };
    ```
  </Tab>

  <Tab title="Multi-Sort">
    ```ts
    // import { SortDirection } from '@ptc-org/nestjs-query-core';
    const q: Query<MyClass> = {
      sorting: [
        { field: 'title', direction: SortDirection.DESC },
        { field: 'age', direction: SortDirection.ASC },
      ],
    };
    ```
  </Tab>
</Tabs>

## Filter Reference[​](#filter-reference 'Direct link to Filter Reference')

The `filter` option supports the following field comparisons.

<Note>
  The following examples show an approximation of the SQL that will be generated. The ORM will take care of handling the dialect
  specifics
</Note>

### Common Comparisons[​](#common-comparisons 'Direct link to Common Comparisons')

All types support the following comparisons.

- `is` - Check is a field is `null`, `true` or `false`.
  ```ts
  // title IS NULL
  {
    title: {
      is: null
    }
  }
  // completed IS TRUE
  {
    completed: {
      is: true
    }
  }
  // completed IS false
  {
    completed: {
      is: false
    }
  }
  ```
- `isNot` - Check is a field is not `null`, `true` or `false`.
  ```ts
  // title IS NOT NULL
  {
    title: {
      isNot: null
    }
  }
  // completed IS NOT TRUE
  {
    completed: {
      isNot: true
    }
  }
  // completed IS NOT false
  {
    completed: {
      isNot: false
    }
  }
  ```
- `neq` - field is not equal to a value.
  ```ts
  // title != 'foo'
  {
    title: {
      neq: 'foo'
    }
  }
  ```
- `gt` - field is greater than a value.
  ```ts
  // title > 'foo'
  {
    title: {
      gt: 'foo'
    }
  }
  ```
- `gte` - field is greater than or equal to a value.
  ```ts
  // title >= 'foo'
  {
    title: {
      gte: 'foo'
    }
  }
  ```
- `lt` - field is less than a value.
  ```ts
  // title < 'foo'
  {
    title: {
      lt: 'foo'
    }
  }
  ```
- `lte` - field is less than or equal to a value.
  ```ts
  // title <= 'foo'
  {
    title: {
      lte: 'foo'
    }
  }
  ```
- `in` - field is in a list of values.
  ```ts
  // title IN ('foo', 'bar', 'baz')
  { title: { in: ['foo', 'bar', 'baz'] } }
  ```
- `notIn` - field is not in a list of values.
  ```ts
  // title NOT IN ('foo', 'bar', 'baz')
  {
    title: {
      notIn: ['foo', 'bar', 'baz']
    }
  }
  ```

### String Comparisons[​](#string-comparisons 'Direct link to String Comparisons')

- `like` - field is like a value (case sensitive).
  ```ts
  // title LIKE 'Foo%'
  {
    title: {
      like: 'Foo%'
    }
  }
  ```
- `notLike` - field is not like a value (case sensitive).
  ```ts
  // title NOT LIKE 'Foo%'
  {
    title: {
      notLike: 'Foo%'
    }
  }
  ```
- `iLike` - field is like a value (case insensitive).
  ```ts
  // title ILIKE 'Foo%'
  {
    title: {
      iLike: 'Foo%'
    }
  }
  ```
- `notILike` - field is not like a value (case insensitive).
  ```ts
  // title NOT ILIKE 'Foo%'
  {
    title: {
      notILike: 'Foo%'
    }
  }
  ```
